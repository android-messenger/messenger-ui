# Tasks: Путь сообщения — ничего не теряется и всё покрыто тестами

**Input**: [spec.md](spec.md), [test-matrix.md](test-matrix.md), отчёт [../002-reliable-delivery/audit.md](../002-reliable-delivery/audit.md)

**Формат**: `[ID] [P?] [История] Описание`. `[P]` — можно делать параллельно с соседними: другие файлы, нет зависимости. Пути — от корня репозитория.

**Правила работы**

- Одна история — одна ветка от свежего `main` и один PR. Имя ветки указано у истории. Большая история 2 идёт тремя PR (2а, 2б, 2в).
- **Сначала тест.** Тест сценария пишется первым и падает на `main`; потом правка. Для A1–A7 тест уже есть: он переворачивается в том же PR.
- Тест пути сообщения идёт на стенде (история 1). Подделывать `chatApi`, `chatMessages.service`, `sendOutboxThunk`, хранилище истории нельзя (FR-006).
- Название теста начинается с номера сценария; строка в `test-matrix.md` заполняется в том же PR.
- Перед PR: `npm run ci` и `npm run build:app` из `front/`. Порог покрытия не снижается.
- Задача отмечается `[x]` в том же PR. Статус истории в `spec.md` и отметка находки в `audit.md` — там же.
- Слияние PR — без отдельного вопроса. Выкатка веб-образа и публикация APK — только по слову владельца.
- Что не проверено, пишется в PR прямо.

**Как устроено слияние (T311, `mergeHistory.ts`).** Ответ сервера говорит о диапазоне: от своей первой строки до момента, когда сервер прочитал таблицу. Внутри диапазона прав сервер — строки, которой нет в ответе, больше нет. Вне диапазона чат оставляет своё: строки старше первой строки ответа (если ответ — не вся история, то есть в нём полная страница), строки, пришедшие по сокету **после отправки запроса**, и свои неотправленные. Поэтому срезу (T312) нужно помнить по каждому чату, какие строки пришли по сокету, пока запрос идёт, — функция получает их номера в `arrived`. Одинаковый клиентский номер — одна строка; строка ответа приносит время сервера и сохраняет расшифрованный на устройстве текст.

**К T312–T314 — замечание о порядке.** После T313 экран читает сообщения из среза, а остальные писатели (удаление, эхо, старые страницы, восстановление секретного текста) по плану переезжают только в 2б и 2в. Чтобы между PR ничего не ломалось, в 2а им нужен общий переходный вход — «исправить строки чата» в срезе, — на который в 2а механически переводятся все `updateQueryData("getChatHistory", …)`; 2б и 2в заменяют его отдельными действиями.
