# 002 — Надёжный приём сообщений и уведомлений

Состояние: **черновик на обсуждение**, 2026-11-14. Кода нет.
Повод: владелец на телефоне (сборки 10097–10190, обычные сообщения между браузером и телефоном) видел два сбоя:
**А** — уведомление не пришло; **Б** — уведомление пришло, приложение открыто, нового сообщения нет.

## 1. Контракт (слова владельца)

1. Сервер доставляет сообщение по WebSocket и ждёт подтверждения.
2. Сокет закрыт — доставка отменяется, сообщение остаётся в истории.
3. Push уходит, когда: (а) отправлено, подтверждения нет, идёт вторая попытка; (б) сокет закрыт, сообщение ушло только в историю.
4. Клиент, получив сообщение: подтверждает; чат открыт — показывает сообщение; чат не открыт — ставит отметку «непрочитано».
5. Приложение не на экране — нужно нативное уведомление, есть сокет или нет. Без потерь и без дублей.
6. Приложение вернулось и восстановило сокет — пропущенное перечитывается из истории (REST).

## 3. Дизайн

Одно правило вместо набора частных случаев:

> **История — источник правды. Сокет — только ускорение. То, что показано, считается полным, лишь пока клиент может это доказать.**

### 3.1. Признак «в сокете был разрыв» (ответ на вопрос владельца)

Да, такой признак возможен, и он лучше, чем «перечитывать всегда». Он уже наполовину есть: счётчик соединений сокета (`ws.epoch`) растёт на каждое новое соединение.

- У каждого чата в памяти — номер соединения, при котором его история была **прочитана с сервера** (`syncedEpoch`). Номер берётся в момент начала запроса и только если сокет в этот момент соединён.
- История чата **полная**, если `syncedEpoch` равен текущему номеру соединения и сокет с тех пор не рвался. Иначе чат **устарел**.
- Любой разрыв — уход в фон, обрыв сети, вытеснение другой сессией, принудительное закрытие сервером, перезагрузка страницы — меняет номер. Значит, после любого разрыва устарели все чаты разом, без перечисления причин.
- Устаревший чат перечитывается: открытый — сразу после соединения; остальные — при открытии. Не устаревший не перечитывается вовсе.
- Пока устаревший чат перечитывается, показано старое и строка «обновляется»; ошибка чтения — строка «не удалось обновить, повторить», а не тишина.

Почему этого достаточно: сервер, не получив подтверждения, после нескольких попыток сам закрывает сокет — то есть «тихой» потери внутри живого соединения нет, она всегда кончается разрывом, а разрыв меняет номер.

Чего признак не ловит: сокет «открыт, но мёртв» (сеть пропала без закрытия). Для этого — сторож: нет ни одного кадра дольше порога — сокет закрывается и соединяется заново. Порог и кадр проверки — задача T205.

### 3.2. Отметка «непрочитано» — с сервера, а не из сокета

Проверено по коду сервера (T200): время активности чата (`updatedAt`) сообщениями **не меняется**, на нём строить нельзя. Зато сервер уже отдаёт всё нужное:

- список чатов несёт **мою позицию прочтения** в каждом чате (номер последнего прочитанного сообщения);
- история отдаёт **последнее сообщение** чата коротким запросом (`limit=1`).

Правило: чат «непрочитан», если его последнее сообщение не моё и его номер больше моей позиции прочтения.

- После каждого соединения сокета (то есть после любого разрыва) список чатов перечитывается — это уже так. Затем для каждого чата спрашивается последнее сообщение, не больше четырёх запросов разом, сначала самые свежие чаты; предел — 50 чатов.
- Кадр сокета ставит отметку сразу, как сейчас. Опрос — вторая, независимая дорога: работает и после push, и после потерянного push, и после холодного запуска.
- Отметка снимается, когда пользователь смотрит на чат (позиция прочтения уходит на сервер, как сейчас).
- Группы: список групп позицию прочтения не несёт — для них отметка ставится только кадром сокета и нажатием на уведомление. Запись в этап 2.
- Цена — до 50 коротких запросов на каждое соединение. На этапе 2 сервер отдаст номер последнего сообщения прямо в списке чатов (задача S8), и опрос станет не нужен.

### 3.3. Уведомления: один судья — приложение

- Правило: **сообщение пришло, а пользователь на этот чат не смотрит — нативное уведомление.** Каким путём пришло, неважно.
- Сообщение принято по сокету, когда приложение не на экране (окно при сворачивании, звонок, выбор файла) — интерфейс просит приложение показать уведомление: номер чата, номер сообщения.
- Дубли убирает приложение по номеру сообщения — тем же списком, которым уже убирает повторные push. Push и сокет несут один и тот же номер.
- Подтверждение серверу интерфейс шлёт после того, как сообщение положено в память **и** уведомление заказано. Не успел — сервер повторит или пришлёт push.
- Уведомление без номера чата (push не расшифровался): нажатие открывает список чатов; непрочитанный виден по 3.2.

### 3.4. Отметка «вышел» и регистрация push

- Отметка ставится только настоящим выходом. Сбой сети при проверке сессии — не выход: ничего не стирать, проверить позже.
- Регистрация push повторяется до успеха: при запуске, возврате на экран, появлении сети.
- Уборка не трогает токен, пока сессия жива.
- Пока отметка стоит при живой сессии — строка в журнале и на экране «Инфо».

### 3.5. Журнал

Каждое решение — одной строкой в `logcat` и в журнале интерфейса: push отброшен (причина), уведомление показано или снято, чат устарел (причина), история перечитана (сколько строк, сколько новых), сокет закрыт сторожем. Следующий сбой разбирается по журналу, а не по догадке.

## 4. Чего не делаем на этом этапе

- Сервер и `firebase-push` — этап 2 (§6).
- Чтение «только нового» (`?since=`): на сервере у него дефект (неизвестный номер отдаёт самую старую страницу). Перечитываем последнюю страницу целиком, как сейчас.
- Синхронизация между несколькими устройствами одного пользователя: сервер держит одну сессию на пользователя.

## 5. Готово, когда

На телефоне, с журналом, по 5 раз каждый случай, без единого сбоя:

1. Приложение свёрнуто, сообщение — уведомление; нажатие — сообщение видно.
2. Приложение свёрнуто, сообщение, открыть значком — чат отмечен «непрочитано», сообщение в нём есть.
3. Сообщение в ту секунду, когда приложение сворачивается, — уведомление есть, одно.
4. Сообщение во время звонка при свёрнутом приложении — уведомление есть, одно.
5. Открыт чат А, сообщение в чат Б — отметка у Б; нажатие на уведомление Б — сообщение видно.
6. Режим полёта на минуту при открытом чате, сообщение в это время — после сети видно без действий.
7. Приложение убито, сообщение, запуск — отметка и сообщение.
8. Сбой сети на странице входа — push продолжают приходить после входа.
9. Ни в одном случае нет двух уведомлений на одно сообщение.

## 6. Этап 2 — сервер (отложено, слово владельца 2026-11-14)

Сюда же относится задача «ограничить срок WebSocket-сессии» (`docs/specs/S3-gateway.md` §5.8).

- S1. Сокет закрылся, а отправленное сообщение не подтверждено — push (находка 7). **Первая задача этапа** — см. 6.1.
- S2. Вторая попытка не шлёт push на подтверждённое сообщение (находка 8). Делается вместе с S1 — см. 6.1.
- S3. Ошибка базы при чтении истории — ошибка, а не пустой список (находка 9).
- S4. `firebase-push`: ключ склейки — по чату (находка 10).
- S5. `?since=` с неизвестным номером — ошибка, а не самая старая страница.
- S6. Максимальный срок WebSocket-сессии.
- S7. Сбой публикации в Kafka — повтор, а не потеря.
- S8. Список чатов и список групп отдают номер последнего сообщения и позицию прочтения — вместо опроса по одному чату (§3.2).
- S9. Кадр проверки живости сокета, на который сервер отвечает (для сторожа, T205).
- S10. Склейка `CHAT_IN` по клиентскому номеру: второй кадр с тем же номером от того же отправителя в том же чате — то же сообщение, а не новая строка, новый `CHAT_OUT` и новый push (находка 7 аудита). Клиент с `messenger-ui` № 35 шлёт один кадр на соединение; повтор после разрыва и повтор от прежних версий клиента склеить может только сервер.
- S11. Номер чата в `CHAT_ACK` (находка 10 аудита). Клиент берёт чат из своей очереди и без него; номер нужен, когда записи в очереди уже нет.

### 6.1. S1 и S2 — замысел (сессия 52, 2026-11-16, согласовано с владельцем)

**Что найдено на телефоне** (A37, APK 10192, подробно — `docs/HANDOFF.md`, сессия 52, вторая часть). Приложение уходит в фон, веб-клиент закрывает сокет (`close(1000)`) за ~0,8 с, а до сервера закрытие доходит через ~4 с (журнал nginx; из браузера на компьютере — в ту же секунду, значит задержка в телефоне). Сообщение в этом окне сервер пишет в умирающий сокет. Дальше на сервере гонка: `PresenceCoordinator.leave()` → `fireRemove` убирает клиента из водяного знака, сборщик (раз в 10 с) удаляет его неподтверждённые строки outbox — `OfflineEscalationStage` (`processing_attempts == 2`) до них не доходит, push нет; если повторная выдача (аренда 10 с) успела раньше — получатель уже не в сети, push через ~14 с. Итог по случаю 3 §5: уведомление 2 из 5, оба через ~14 с. Сообщение не теряется: оно в истории. Находка 8 видна там же: через ~13 с после подтверждённой доставки приходит лишний push (приложение отбрасывает его по номеру сообщения).

**Решение: таблица неподтверждённых в сессии сокета.** Outbox и Tetris не трогаем: outbox — лишние запросы к базе на каждый разрыв, Tetris — отдельная библиотека (`messenger-hl`) и гонка с его уборкой.

- В сессии сокета (реестр сессий, `infrastructure/websocket`) — ограниченная синхронная таблица «чат → номера ушедших и не подтверждённых сообщений + данные для push по последнему». Не кольцевой буфер: подтверждения приходят не по порядку и вычёркивают номер из середины.
- Доставка удалась (`DeliveryStage`, успех) → номер добавляется. `CHAT_ACK` (`AckStage`) → номер вычёркивается, пустой чат убирается. Из `core` — через новый порт в `ports/` (роль-существительное, без «Repository»), реализация — в `infrastructure/websocket`; правила `HexagonalArchitectureTest` не ослаблять.
- Только `CHAT_OUT` и `SYSTEM_OUT` (то же, что `pushOfflineNudge`).
- Размер: до 64 номеров на сессию (клиент с более чем 20 неподтверждёнными и так выкидывается, `session.max-pending`). При переполнении номера не нужны — остаётся отметка «в этом чате есть неподтверждённое»: push всё равно склеивается по чату.
- **Разрыв** — `PresenceCoordinator.leave()`, до `fireRemove`: под замком сессии поставить «закрыта» и забрать таблицу; на каждый чат с остатком — один `OfflinePusher.push(...)`; дальше как сейчас (сборщик чистит outbox, история остаётся). Проверить по коду, что в `leave()` приходят все пути: `onClose`, `onError` (`HttpClosedException`), уборщик по тишине (`idle-timeout-ms`), выкидывание за `max-pending` и `max-delivery-attempts`.

**Гонки:**
- Доставка записана после разрыва: добавление под тем же замком видит «закрыта» и шлёт push само.
- Подтверждение ещё в обработке, когда сокет закрылся: лишний push на подтверждённое сообщение — безвредно (приложение отбрасывает по номеру; один push на чат).
- Пользователь уже переподключился новым сокетом: push не слать (новое соединение дочитает историю).

**S2 заодно:** `OfflineEscalationStage` перед push смотрит таблицу сессии получателя — номера нет (подтверждено) или сессии нет (тогда push уже ушёл при разрыве или через `passive()`) — push не нужен.

**Не покрывается:** перезапуск сервера (таблица в памяти пропадает — как и сейчас; приложения переподключаются и дочитывают историю); несколько экземпляров сервера — таблица у каждого своя, а сессия пользователя живёт на одном экземпляре, так что работает и тогда.

**Готово, когда:** на телефоне случаи 1–3 §5 по 5 раз — уведомление каждый раз, в пределах ~5 с после ухода в фон (окно телефона ~4 с), ни одного двойного; лишних push на подтверждённое (`push: drop` в журнале `Wolp`) — нет. Проверка — тем же способом, что в сессии 52 (тестовые `diag-probe*`, браузер без интерфейса, `logcat`, журнал nginx). Тесты сервера: модульные на таблицу (добавить, вычеркнуть, переполнение, закрыта → push сразу) и на `leave()`; e2e (Node WS) — сообщение в сокет без `CHAT_ACK`, закрыть сокет → событие в `chat.offline.notify`.

**Клиент после этапа 2** (по результатам той же проверки): случай 5 §5 — уведомление о сообщении в другой чат при открытом приложении не показывается (`notify.ts` `tellApp` передаёт `hidden` только при скрытой странице; `PushRules.socketMessage` в `wolp-android`); регистрация push после смены сети не повторяется до следующего запуска (`WolpApp.cleanUpAfterSignOut`).
