# 002 — Надёжный приём сообщений и уведомлений

Состояние: **черновик на обсуждение**, 2026-11-14. Кода нет.
Повод: владелец на телефоне (сборки 10097–10190, обычные сообщения между браузером и телефоном) видел два сбоя:
**А** — уведомление не пришло; **Б** — уведомление пришло, приложение открыто, нового сообщения нет.

## 1. Контракт (слова владельца)

1. Сервер доставляет сообщение по WebSocket и ждёт подтверждения.
2. Сокет закрыт — доставка отменяется, сообщение остаётся в истории.
3. Push уходит, когда: (а) отправлено, подтверждения нет, идёт вторая попытка; (б) сокет закрыт, сообщение ушло только в историю.
4. Клиент, получив сообщение: подтверждает; чат открыт — показывает сообщение; чат не открыт — ставит отметку «непрочитано».
5. Приложение не на экране — нужно нативное уведомление, есть сокет или нет. Без потерь и без дублей.
6. Приложение вернулось и восстановило сокет — пропущенное перечитывается из истории (REST).

## 3. Дизайн

Одно правило вместо набора частных случаев:

> **История — источник правды. Сокет — только ускорение. То, что показано, считается полным, лишь пока клиент может это доказать.**

### 3.1. Признак «в сокете был разрыв» (ответ на вопрос владельца)

Да, такой признак возможен, и он лучше, чем «перечитывать всегда». Он уже наполовину есть: счётчик соединений сокета (`ws.epoch`) растёт на каждое новое соединение.

- У каждого чата в памяти — номер соединения, при котором его история была **прочитана с сервера** (`syncedEpoch`). Номер берётся в момент начала запроса и только если сокет в этот момент соединён.
- История чата **полная**, если `syncedEpoch` равен текущему номеру соединения и сокет с тех пор не рвался. Иначе чат **устарел**.
- Любой разрыв — уход в фон, обрыв сети, вытеснение другой сессией, принудительное закрытие сервером, перезагрузка страницы — меняет номер. Значит, после любого разрыва устарели все чаты разом, без перечисления причин.
- Устаревший чат перечитывается: открытый — сразу после соединения; остальные — при открытии. Не устаревший не перечитывается вовсе.
- Пока устаревший чат перечитывается, показано старое и строка «обновляется»; ошибка чтения — строка «не удалось обновить, повторить», а не тишина.

Почему этого достаточно: сервер, не получив подтверждения, после нескольких попыток сам закрывает сокет — то есть «тихой» потери внутри живого соединения нет, она всегда кончается разрывом, а разрыв меняет номер.

Чего признак не ловит: сокет «открыт, но мёртв» (сеть пропала без закрытия). Для этого — сторож: нет ни одного кадра дольше порога — сокет закрывается и соединяется заново. Порог и кадр проверки — задача T205.

### 3.2. Отметка «непрочитано» — с сервера, а не из сокета

- Для каждого чата хранится (запечатанной записью) время последнего сообщения, которое пользователь видел.
- Список чатов с сервера несёт время последней активности чата (`updatedAt`). После каждого соединения список перечитывается (это уже так). Активность новее виденного — чат отмечен «непрочитано» и считается устаревшим.
- Кадр сокета ставит отметку сразу, как сейчас. Список — вторая, независимая дорога: работает и после push, и после потерянного push, и после холодного запуска.
- Проверить до кода (T200): что `updatedAt` меняется на каждое сообщение и не меняется от прочтения.

### 3.3. Уведомления: один судья — приложение

- Правило: **сообщение пришло, а пользователь на этот чат не смотрит — нативное уведомление.** Каким путём пришло, неважно.
- Сообщение принято по сокету, когда приложение не на экране (окно при сворачивании, звонок, выбор файла) — интерфейс просит приложение показать уведомление: номер чата, номер сообщения.
- Дубли убирает приложение по номеру сообщения — тем же списком, которым уже убирает повторные push. Push и сокет несут один и тот же номер.
- Подтверждение серверу интерфейс шлёт после того, как сообщение положено в память **и** уведомление заказано. Не успел — сервер повторит или пришлёт push.
- Уведомление без номера чата (push не расшифровался): нажатие открывает список чатов; непрочитанный виден по 3.2.

### 3.4. Отметка «вышел» и регистрация push

- Отметка ставится только настоящим выходом. Сбой сети при проверке сессии — не выход: ничего не стирать, проверить позже.
- Регистрация push повторяется до успеха: при запуске, возврате на экран, появлении сети.
- Уборка не трогает токен, пока сессия жива.
- Пока отметка стоит при живой сессии — строка в журнале и на экране «Инфо».

### 3.5. Журнал

Каждое решение — одной строкой в `logcat` и в журнале интерфейса: push отброшен (причина), уведомление показано или снято, чат устарел (причина), история перечитана (сколько строк, сколько новых), сокет закрыт сторожем. Следующий сбой разбирается по журналу, а не по догадке.

## 4. Чего не делаем на этом этапе

- Сервер и `firebase-push` — этап 2 (§6).
- Чтение «только нового» (`?since=`): на сервере у него дефект (неизвестный номер отдаёт самую старую страницу). Перечитываем последнюю страницу целиком, как сейчас.
- Синхронизация между несколькими устройствами одного пользователя: сервер держит одну сессию на пользователя.

## 5. Готово, когда

На телефоне, с журналом, по 5 раз каждый случай, без единого сбоя:

1. Приложение свёрнуто, сообщение — уведомление; нажатие — сообщение видно.
2. Приложение свёрнуто, сообщение, открыть значком — чат отмечен «непрочитано», сообщение в нём есть.
3. Сообщение в ту секунду, когда приложение сворачивается, — уведомление есть, одно.
4. Сообщение во время звонка при свёрнутом приложении — уведомление есть, одно.
5. Открыт чат А, сообщение в чат Б — отметка у Б; нажатие на уведомление Б — сообщение видно.
6. Режим полёта на минуту при открытом чате, сообщение в это время — после сети видно без действий.
7. Приложение убито, сообщение, запуск — отметка и сообщение.
8. Сбой сети на странице входа — push продолжают приходить после входа.
9. Ни в одном случае нет двух уведомлений на одно сообщение.
