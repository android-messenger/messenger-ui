## Контекст

`messenger-ui` — интерфейс мессенджера. Он работает в двух видах: упакованным в приложение для Android (основной) и в браузере (только на время тестирования).

Проверка безопасности 2026-11-11 нашла в интерфейсе дефекты секретных чатов. Номера находок — из `docs/security/findings.md`.

**Что уже сделано:**

- находка № 1 (расшифрованный текст в кэше истории, черновики на диске) — исправлена в PR #16, слита в `main` (`b36cb09`). На стенд и в APK не выкачена, вручную не проверена;
- находка № 4 (в APK нет CSP) — исправление написано в PR #14, не слито: не проверено на телефоне.

**Что осталось** и чем закрывается:

| № | Находка | История |
|---|---|---|
| 13 | выход из аккаунта не стирает ключи и данные секретных чатов | 1 |
| — | на PR нет автоматических проверок; `tsc` даёт 15 старых ошибок, `eslint` — 5 | 2 |
| 4 | у интерфейса в APK нет CSP | 3 |
| 15 | секретный режим не согласован между собеседниками и теряется | 4 |

| 50 | адрес STUN по умолчанию — чужой сервер | 5 |

| 48 | код безопасности: 1024 итерации; отметка «сверено» в `localStorage` | 6 |

**Почему находки 14, 40, 45, 48 не чинятся в JavaScript.** По принятому дизайну (`docs/specs/F3-key-protection-design.md`, решение 3) ключи, сессии и отметки сверки переезжают в нативную библиотеку приложения. Код, который эти находки затрагивает, в приложении будет удалён. Чинить его сейчас — работа на выброс.

**Что сверено с кодом при написании** (`main` = `b36cb09`):

- `store/logout.ts` чистит `chatDB` и черновики; базы `e2ee-*` и ключи `localStorage` со списком секретных чатов и с отметками «сверено» не трогает. `clearSecretChats` и `clearDeviceKey` объявлены, но нигде не вызываются;
- секретный режим — флажок в `localStorage` на одном устройстве (`secretChatsSlice.ts`); собеседнику он не передаётся;
- `atRest.ts` `savePlaintext` глотает любую ошибку (`catch { /* best-effort */ }`);
- `deviceKey.ts` `vaultCall` повторяет вызов после `VAULT_LOCKED` без предела и без сигнала пользователю;
- `shared/config/webrtc.ts` — умолчание: адрес и порт чужого сервера;
- `npx tsc -b` — 15 ошибок в 7 файлах; `npx eslint .` — 5 ошибок в 4 файлах.

Связанные документы: `docs/specs/F1-e2ee-critical-fixes.md` (работа 1 выполнена; «Работа 2» написана до F3 и заменяется историей 6), `docs/specs/F3-key-protection-design.md`, `docs/security/02-e2ee.md`, `docs/security/findings.md`.

## Clarifications

### Session 2026-11-12

Q1, Q2 и Q3 решены владельцем.

- Q1 (история 1): стирать ключи и секретную историю при каждом выходе или только когда на устройстве входит другой пользователь? → A: **При каждом выходе** (владелец, 2026-11-12). Вышел и вошёл снова — секретной истории нет, собеседники видят смену ключа.
- Q2 (история 4): можно ли вернуть секретный чат в обычный режим? → A: сначала «нельзя», затем владелец изменил решение в тот же день: **можно, по желанию, без ограничений** («можно разрешить переключаться с секретных на несекретные режимы чата по желанию, без ограничений», 2026-11-12). Выключает режим только сам пользователь, кнопкой в заголовке чата; ничто пришедшее с сервера режим не выключает.
- Q3 (история 6): какая реализация протокола в нативной библиотеке и её лицензия (F3 §8, вопрос 1)? → A: **`libsignal`** (владелец, 2026-11-12: «готов открывать весь код приложения»). Оценка лицензий здесь не юридическая.

  | Вариант | Лицензия | Состояние | Вывод |
  |---|---|---|---|
  | `vodozemac` (Matrix, Rust) | Apache-2.0 | развивается, версия 0.11.2; аудит Least Authority 2022 | **подходит закрытому приложению**; собирается и для телефона, и для браузера (WebAssembly) |
  | `libsignal` (Signal, Rust + Java) | AGPL-3.0 | развивается, версия 0.107.0 | настоящий протокол Signal с постквантовой защитой. Под AGPL пришлось бы открыть весь APK: интерфейс, приложение и библиотеку устройства вместе с RASP. Сборки для браузера нет; с нынешним браузерным клиентом несовместим: сессии без постквантового ключа отклоняет («X3DH no longer supported»). В README: «Use outside of Signal is unsupported», интерфейсы меняются без предупреждения |
  | `libsignal-protocol-java`, `libsignal-protocol-c` | GPL-3.0 | архив, не поддерживаются с 2020–2021 | не брать |
  | `@privacyresearch/libsignal-protocol-typescript` (нынешняя) | GPL-3.0-only | последний коммит 2023 | только JavaScript; из-за неё `messenger-ui` под GPL |
  | своя реализация по открытым спецификациям Signal | своя | — | не брать: криптография без аудита |

  Следствия выбора `libsignal`:

  - **Код открывается под AGPL-3.0**: `messenger-ui`, `wolp-android`, `wolp-device-trust` (вместе с RASP). Обязанность возникает, когда APK с библиотекой получает кто-то вне команды: получатель должен иметь доступ к исходникам этой сборки. Ключи подписи, пароли и настройки сервера исходниками не являются. Шлюз и служба ключей библиотеку не содержат и не затрагиваются.
  - **Секретные чаты между браузером и телефоном перестают работать**: сборки `libsignal` для браузера нет. Обычные чаты работают; секретные проверяются на двух телефонах.
  - **Служба ключей** получает ещё один вид ключа в записи (постквантовый prekey).
  - **Signal чужое использование не поддерживает**: версия библиотеки закрепляется, каждое обновление проверяется.
  - Не проверено: размер библиотеки в APK, сборка под наш NDK и `minSdk` 33, история коммитов трёх репозиториев на секреты перед открытием.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Выход из аккаунта не оставляет ключей и секретной переписки (Priority: P1)

Пользователь выходит из аккаунта. На устройстве не остаётся его ключей, секретной переписки и отметок. Следующий, кто войдёт на этом устройстве, ничего не наследует.

**Why this priority**: сейчас ключи первого пользователя достаются второму: тот читает чужую секретную историю и пишет от чужого ключа. Исправление не зависит ни от нативной библиотеки, ни от телефона.

**Independent Test**: тест на настоящих IndexedDB и `localStorage`: после выхода баз `e2ee-*` и ключей нет; вход другого пользователя начинает с пустого состояния.

**Статус**: код и тесты слиты в `main` (ветка `001-logout-wipe`). Сценарии 1.1–1.7 покрыты тестами. Не выкачено; вручную в браузере и на телефоне не проверено. Документы (`docs/security`) не обновлены.

**Acceptance Scenarios**:

1. **Given** у пользователя есть ключи, секретная история и отметка «сверено», **When** он выходит, **Then** баз `e2ee-device`, `e2ee-signal`, `e2ee-plaintext`, `e2ee-recovery` нет, ключей `localStorage` со списком секретных чатов и с отметками «сверено» нет.
2. **Given** пользователь А вышел, **When** на том же устройстве входит пользователь Б, **Then** Б получает новый ключ; секретной истории А и его списка секретных чатов у Б нет.
3. **Given** сессия ещё действует, **When** пользователь выходит, **Then** его запись удаляется из службы ключей; собеседник при отправке получает «у получателя нет ключей», а не шифрует на мёртвый ключ.
4. **Given** служба ключей недоступна или отвечает отказом, **When** пользователь выходит, **Then** выход и стирание на устройстве всё равно завершаются.
5. **Given** стирание прервано (вкладку закрыли, приложение убито), **When** интерфейс запускается снова, **Then** стирание доводится до конца раньше, чем читается любой ключ.
6. **Given** на устройстве остались данные другого пользователя (старая версия интерфейса, сбой), **When** входит новый пользователь, **Then** чужие данные стираются до первого использования.
7. **Given** сессия истекла сама и пользователь снова вошёл под тем же именем, **When** интерфейс запускается, **Then** ключи и история на месте — истечение сессии не выход.

### User Story 2 - Каждый PR проверяется автоматически (Priority: P2)

Разработчик открывает PR. Тесты, линтер, проверка типов и обе сборки запускаются сами. Владелец на GitHub видит по PR, прошли проверки или нет.

**Why this priority**: сейчас проверки запускаются только вручную и только у автора. Все следующие истории меняют шифрование — им нужна проверка, которая не зависит от памяти автора.

**Independent Test**: PR с намеренно сломанным тестом получает красную отметку; PR с исправлением — зелёную.

**Статус**: сделано, кроме запрета слияния без проверок. `npm run ci` на `main` проходит: 15 ошибок `tsc` и 5 ошибок `eslint` исправлены, правила не отключались. Workflow `.github/workflows/ci.yml` идёт на каждом PR и на каждом коммите в `main`; на PR проверено, что сломанный тест даёт красную отметку. Сценарий 4 (GitHub не даёт слить) не выполнен: обязательная проверка для `main` в настройках репозитория не включена (T015).

**Acceptance Scenarios**:

1. **Given** PR в `main`, **When** он открыт или обновлён, **Then** выполняются линтер, проверка типов, тесты, веб-сборка и сборка для APK; результат виден в PR.
2. **Given** `main` после этой истории, **When** запускается `npm run ci`, **Then** он проходит без ошибок: 15 прежних ошибок `tsc` и 5 ошибок `eslint` исправлены, а не отключены.
3. **Given** PR убрал или испортил байт-разделитель в `chatApi.ts` или `chatMessages.service.ts`, **When** идут проверки, **Then** они падают (до истории 5 — проверка числа байтов NUL; после неё — обычный тест).
4. **Given** проверки не прошли, **When** PR пытаются слить, **Then** GitHub не даёт.

### User Story 3 - У интерфейса в приложении есть CSP (Priority: P3)

Интерфейс в APK загружает и исполняет только собственный код и обращается только к своим серверам. Чужой скрипт, попавший на страницу, не исполняется и не достаёт до моста с защищённым хранилищем.

**Why this priority**: находка высокая, код готов (PR #14). Стоит третьей только потому, что без прохода на телефоне сливать нельзя.

**Independent Test**: APK со сборкой из ветки `app-csp`, полный проход по функциям на Galaxy A37, журнал без нарушений политики.

**Статус**: код в PR #14, не слит. Нужны сборка APK и телефон по USB.

**Acceptance Scenarios**:

1. **Given** сборка для APK, **When** она завершена, **Then** в `index.html` политика стоит первой в `<head>`; без политики или со встроенным скриптом сборка падает.
2. **Given** APK с этой сборкой на телефоне, **When** пользователь входит, открывает обычный и секретный чат, отправляет и получает вложение, делает аудио- и видеозвонок, получает push и открывает чат касанием уведомления, **Then** всё работает, в журнале нет ни одного нарушения политики.
3. **Given** страница пытается исполнить встроенный скрипт или обратиться к постороннему адресу, **When** это происходит, **Then** запрос отклонён политикой.

### User Story 4 - Секретный чат секретен у обоих и не становится обычным молча (Priority: P4)

Пользователь включил секретный режим. Собеседник тоже видит чат секретным и отвечает зашифрованно. Если устройство потеряло свои настройки, чат не превращается в обычный без ведома пользователя.

**Why this priority**: сейчас флажок живёт на одном устройстве. Собеседник отвечает открытым текстом в чат, который первый считает секретным. После очистки `localStorage` пользователь продолжает писать открыто и не знает об этом.

**Independent Test**: тест на двух клиентах в памяти: первый включает режим и пишет; второй без единого действия отвечает зашифрованно.

**Статус**: реализовано и слито в `main`, не выкачено. Чат становится секретным по первому зашифрованному сообщению (живому или из истории); режим включается с подтверждением и не выключается; открытое сообщение после зашифрованного помечается «не зашифровано»; секретный чат без получателя не отправляет ничего. Проверено тестами (сценарии 4.1–4.5). Не проверено: вручную в браузере и на телефоне. Ограничения: пометка «не зашифровано» ставится только сообщениям после первого зашифрованного в загруженной истории; вложения в секретном чате не шифруются и получают эту пометку. **Изменено 2026-11-12 по слову владельца:** режим выключается кнопкой в заголовке чата, с подтверждением; выключить его может только пользователь.

**Acceptance Scenarios**:

1. **Given** чат обычный у обоих, **When** от собеседника приходит зашифрованное сообщение, **Then** чат становится секретным и у получателя; его ответ уходит зашифрованным.
2. **Given** секретный чат и стёртый `localStorage`, **When** интерфейс загружает историю и видит в ней зашифрованные сообщения, **Then** чат снова помечен секретным до первой отправки.
3. **Given** секретный чат, **When** шифрование невозможно (нет ключей собеседника, хранилище закрыто), **Then** сообщение не уходит открытым текстом; пользователь видит причину.
4. **Given** секретный чат, **When** от собеседника приходит открытое сообщение, **Then** оно показано с пометкой «не зашифровано».
5. **Given** секретный чат, **When** пользователь ищет способ выключить режим, **Then** такого способа нет.

### User Story 5 - Мелкие дефекты, не зависящие от нативной библиотеки (Priority: P5)

Пользователь не теряет текст секретного сообщения из-за молча проглоченной ошибки и видит, когда приложение ждёт разблокировки телефона. Сборка не обращается к чужому серверу. В исходниках нет невидимых байтов.

**Why this priority**: низкая серьёзность, но каждое исправление маленькое и не будет выброшено при переходе на нативную библиотеку.

**Independent Test**: по тесту на каждую находку.

**Статус**: реализовано и слито в `main`, не выкачено. Сохранение текста повторяется до трёх раз и при неудаче помечает сообщение; ожидание хранилища дольше 5 секунд показывает полосу «разблокируйте телефон» и прекращается при выходе; сборка без `VITE_TURN_HOST` и `VITE_TURN_PORT` падает, умолчаний нет (в том числе в `Dockerfile`); байт NUL заменён на `\0`. Проверено тестами (сценарии 5.1–5.5) и сборками. Не проверено: сценарий 5.2 на телефоне; сборка образа `docker build`.

**Acceptance Scenarios**:

1. **Given** сохранение расшифрованного текста не удалось, **When** сообщение показано, **Then** клиент повторяет сохранение; если не вышло — сообщение помечено «не сохранено на устройстве», ошибка в журнале без текста сообщения.
2. **Given** защищённое хранилище закрыто (телефон заблокирован), **When** операция ждёт дольше 5 секунд, **Then** пользователь видит «разблокируйте телефон»; после разблокировки операция завершается сама.
3. **Given** операция ждёт разблокировки, **When** пользователь выходит из аккаунта, **Then** ожидание прекращается.
4. **Given** сборка без заданных адреса и порта STUN/TURN, **When** она запускается, **Then** сборка падает; адреса по умолчанию в коде нет.
5. **Given** исходники после исправления, **When** в них ищут байт NUL, **Then** его нет; ключ сравнения сообщений даёт те же значения, что раньше.

### User Story 6 - Ключи и шифрование уходят из интерфейса в приложение (Priority: P6)

Пользователь приложения пишет в секретный чат. Закрытые ключи интерфейсу недоступны: он просит приложение зашифровать и расшифровать. Подменённый на сервере ключ собеседника не принимается. Смена ключа собеседника видна в чате.

**Why this priority**: закрывает главную оставшуюся находку (№ 2) и четыре связанные. Стоит последней, потому что зависит от нативной библиотеки (`wolp-device-trust`, `wolp-android`), которой ещё нет, и от решений владельца.

**Independent Test**: тесты интерфейса против подставной реализации моста; затем проход на двух телефонах.

**Статус**: заблокировано. Q3 решён: `libsignal`. Нужны: остальные вопросы F3 §8, готовый мост в приложении. Служба ключей свою часть уже отдаёт (паспорт хранится и выдаётся — `key-directory` #6).

**Acceptance Scenarios**:

1. **Given** интерфейс в приложении, **When** отправляется или принимается секретное сообщение, **Then** интерфейс вызывает операции моста; `vaultUnwrap` с назначением `e2ee` не вызывается ни разу.
2. **Given** служба ключей вернула ключ без паспорта, с неверной подписью или с чужим сертификатом, **When** пользователь отправляет сообщение, **Then** отправка отклонена, пользователь видит причину.
3. **Given** служба ключей вернула у собеседника больше одного устройства, **When** пользователь отправляет сообщение, **Then** отказ.
4. **Given** у собеседника сменился ключ, **When** приходит или уходит следующее сообщение, **Then** в чате появляется служебная строка о смене ключа.
5. **Given** контакт был сверен по коду безопасности и его ключ сменился, **When** пользователь пытается отправить, **Then** отправка остановлена до повторной сверки.
6. **Given** собеседник пишет из браузера, **When** пользователь телефона открывает с ним секретный чат, **Then** секретная отправка отклонена с причиной «собеседник не в приложении»; обычный чат работает.
7. **Given** звонок, **When** идёт обмен параметрами соединения, **Then** они шифруются теми же операциями; если зашифровать нельзя, звонок не начинается.
8. **Given** приложение обновилось на версию с мостом, **When** интерфейс запускается, **Then** прежние базы ключей интерфейса удалены; собеседники видят смену ключа один раз.

---

### Edge Cases

- Выход при открытых соединениях с базами: удаление откладывается браузером до закрытия соединений. Стирание должно завершиться, а не зависнуть.
- Выход в двух вкладках одновременно; выход в одной вкладке, пока вторая расшифровывает сообщение.
- Выход без сети: запись в службе ключей остаётся. Её заменит следующая публикация ключей того же пользователя.
- При включённом правиле «одно устройство» служба ключей отвечает браузеру `409` на удаление записи телефона — это отказ, выход продолжается.
- Чат, в котором зашифрованные сообщения есть только за пределами загруженной страницы истории.
- Старый клиент собеседника, который отвечает открыто в секретный чат (сценарий 4.4).
- Хранилище закрыто не блокировкой экрана, а защитой приложения (RASP): ожидание не кончится. Пользователь видит состояние, приложение не висит на «расшифровывается».
- Открытые вкладки со старой версией после выкатки веб-образа: нужна перезагрузка.
- Версии веб-образа и APK расходятся: всё, что меняет поведение между собеседниками (история 4), должно работать с собеседником на прежней версии.

## Requirements *(mandatory)*

### Functional Requirements

**История 1 — выход**

- **FR-001**: Выход MUST удалять базы `e2ee-device`, `e2ee-signal`, `e2ee-plaintext`, `e2ee-recovery` и ключи `localStorage` со списком секретных чатов и с отметками «сверено» (имена — в общем списке хранилищ, FR-002).
- **FR-002**: Список хранилищ секретных чатов MUST иметь один источник — для выхода, для «стереть всё» (`wipeStorage.ts`) и для теста, который падает, когда в коде появилась база, не внесённая в список.
- **FR-003**: Пока сессия действует, выход MUST попытаться удалить свою запись из службы ключей. Отказ или недоступность службы MUST NOT останавливать выход.
- **FR-004**: После стирания интерфейс MUST перезагрузиться, чтобы в памяти не осталось открытых ключей и соединений с базами.
- **FR-005**: Начатое стирание MUST доводиться до конца при следующем запуске раньше первого чтения ключей.
- **FR-006**: Данные секретных чатов MUST нести идентификатор владельца. При входе другого пользователя они MUST быть стёрты до первого использования.
- **FR-007**: Истечение сессии без выхода MUST NOT стирать данные.

**История 2 — проверки**

- **FR-010**: На каждый PR и на каждый коммит в `main` MUST выполняться: линтер, проверка типов, тесты, веб-сборка, сборка для APK.
- **FR-011**: Прежние ошибки `tsc` и `eslint` MUST быть исправлены; отключать правила или проверку ради зелёного результата MUST NOT.
- **FR-012**: Слияние в `main` без пройденных проверок MUST быть запрещено настройкой репозитория.
- **FR-013**: Сторонние actions MUST быть закреплены по коммиту, как в `key-directory`.

**История 3 — CSP**

- **FR-020**: Сборка для APK MUST содержать политику первым элементом `<head>` и MUST падать без неё или при встроенном скрипте.
- **FR-021**: Политика MUST разрешать соединения только с адресом API, его WebSocket и хранилищем вложений; встроенные скрипты и `eval` запрещены.
- **FR-022**: PR #14 MUST быть слит только после прохода на телефоне по сценарию 3.2 без нарушений политики.

**История 4 — секретный режим**

- **FR-030**: Чат MUST становиться секретным на устройстве при первом отправленном или принятом зашифрованном сообщении.
- **FR-031**: Отметка MUST восстанавливаться по зашифрованным сообщениям в истории, если локальное состояние потеряно.
- **FR-032**: В секретный чат открытый текст MUST NOT отправляться ни при каком сбое.
- **FR-033**: Открытое сообщение, принятое в секретном чате, MUST показываться с пометкой «не зашифровано».
- **FR-034**: Пользователь MUST мочь включать и выключать секретный режим чата по желанию (решение владельца, Q2). Режим MUST NOT выключаться ничем, кроме действия самого пользователя: открытое сообщение собеседника его не выключает. Зашифрованное сообщение, пришедшее после выключения, MUST включать режим снова; зашифрованные сообщения из истории выключение не отменяют.
- **FR-035**: Поведение MUST сохраняться с собеседником на прежней версии клиента.

**История 5 — мелкие дефекты**

- **FR-040**: Сбой сохранения расшифрованного текста MUST приводить к повтору и, при неудаче, к видимой пометке сообщения. Текст сообщения в журнал MUST NOT попадать.
- **FR-041**: Операция, ждущая разблокировки хранилища дольше 5 секунд, MUST показывать пользователю причину ожидания и MUST прекращаться при выходе. Данные секретных чатов при этом MUST NOT стираться.
- **FR-042**: Адрес и порт STUN/TURN MUST задаваться при сборке; значения по умолчанию MUST быть удалены, сборка без них MUST падать.
- **FR-043**: Разделитель в ключе сравнения сообщений MUST быть записан в исходнике экранированной последовательностью, а не байтом NUL; значения ключа MUST остаться прежними.

**История 6 — мост**

- **FR-050**: Код интерфейса MUST обращаться к шифрованию через один модуль с операциями F3 §3.3: зашифровать, расшифровать, состояние собеседника, код безопасности, отметить или снять «сверено».
- **FR-051**: У модуля MUST быть две реализации: мост приложения и нынешняя браузерная (только тестовая сборка, секретные чаты только между браузерами).
- **FR-052**: В приложении интерфейс MUST NOT получать закрытые ключи и MUST NOT хранить ключи, сессии и отметки сверки.
- **FR-053**: Отказ моста (нет паспорта, неверная подпись, чужой сертификат, больше одного устройства) MUST останавливать отправку с понятной пользователю причиной.
- **FR-054**: Смена ключа собеседника MUST показываться служебной строкой в чате.
- **FR-055**: Сверенному контакту со сменившимся ключом отправка MUST быть остановлена до повторной сверки.
- **FR-056**: Секретная отправка собеседнику без проверенного устройства (в том числе из браузера) MUST отклоняться с понятной причиной.
- **FR-057**: Параметры звонка MUST шифроваться теми же операциями; открытого запасного пути MUST NOT быть.
- **FR-058**: При первом запуске версии с мостом прежние базы ключей интерфейса в приложении MUST быть удалены.

### Key Entities

- **Хранилища секретных чатов** — четыре базы IndexedDB (`e2ee-device`, `e2ee-signal`, `e2ee-plaintext`, `e2ee-recovery`) и два ключа `localStorage`. После истории 6 в приложении остаётся только сохранённый текст.
- **Отметка «секретный чат»** — свойство чата на устройстве; выводится из зашифрованных сообщений, а не только из действия пользователя.
- **Запись в службе ключей** — открытые ключи устройства и, после истории 6, паспорт.
- **Операции моста** — пять операций F3 §3.3 и три добавленные позже: восстановление сообщений, выход из учётной записи, закрытие сообщения о смене ключа (всего восемь, спецификация 002 библиотеки, FR-030); единственный путь интерфейса к шифрованию в приложении.
- **Политика CSP сборки для APK** — `front/csp.app.ts` (PR #14).

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: После выхода на устройстве нет ни одной базы и ни одного ключа из списка FR-001; проверено тестом и вручную в браузере и на телефоне.
- **SC-002**: Пользователь, вошедший после другого на том же устройстве, не видит ни одного его секретного сообщения.
- **SC-003**: 100 % PR в `main` имеют результат автоматических проверок; `npm run ci` на `main` проходит.
- **SC-004**: Полный проход по функциям на телефоне со сборкой с CSP — без единого нарушения политики в журнале.
- **SC-005**: В секретном чате между двумя обновлёнными клиентами ни одно сообщение не уходит открытым текстом, включая первое ответное.
- **SC-006**: Ни один сбой сохранения текста и ни одно ожидание разблокировки дольше 5 секунд не остаются невидимыми для пользователя.
- **SC-007**: В исходниках нет байтов NUL и адресов серверов по умолчанию.
- **SC-008**: В приложении интерфейс не вызывает `vaultUnwrap` с назначением `e2ee`; ключ собеседника, подменённый в базе службы ключей, приводит к отказу отправки на телефоне.
- **SC-009**: Все 14 строк таблицы «Что осталось» в `docs/security/findings.md` имеют состояние «исправлено» со ссылкой на PR либо записанную причину, почему не делается.

## Assumptions

- Браузер — только для тестирования; в проде его нет. Защита проектируется для приложения (решение владельца, F1).
- Одно устройство на пользователя; смена устройства — новые ключи, прежняя секретная история теряется (решение владельца, F3). Выход из аккаунта приравнивается к этому (Q1).
- Нативная библиотека, мост и паспорт делаются в `wolp-device-trust` и `wolp-android` по F3; эта спецификация описывает только сторону интерфейса.
- Находка № 49 (при сбросе хранилища приложение не удаляет `e2ee-recovery`) исправляется в `wolp-android` (`WebData.kt`); здесь — только общий список баз (FR-002).
- Слияние PR — по действующему слову владельца без отдельного вопроса; выкатка веб-образа и публикация APK — только по отдельному слову.
- Изменения в `messenger-ui` не должны ломать собеседника на прежней версии: веб-образ и APK обновляются не одновременно.

## Вне рамок

- Шифрование вложений — `docs/security/13-attachments.md`.
- Обфускация JavaScript в APK — перед выпуском, отдельно.
- Изменения нативной библиотеки, приложения, службы ключей и шлюза.
