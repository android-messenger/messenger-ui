# front — веб-клиент

Интерфейс мессенджера: работает в браузере и внутри приложения Android (сборка `npm run build:app`).

Проверки перед PR — из этого каталога:

```sh
npm run ci          # eslint, tsc, тесты с покрытием, сборка
npm run build:app   # сборка для приложения
```

## Тесты пути сообщения

Путь сообщения — всё между сокетом, хранилищем, диском и экраном: приём, отправка, очередь, история, догон после разрыва. Его тесты лежат в `src/__path__/` и идут на стенде `src/__path__/bench.ts` (спецификация [003](../specs/003-message-path/spec.md)).

### Что настоящее, что подделано

На стенде работает настоящее приложение: хранилище из `configureAppStore`, обработчик сокета, `chatApi`, обработчики кадров, срезы, запись на диск (IndexedDB и `localStorage`).

Стенд играет только то, что снаружи интерфейса:

| Что | Как управлять |
|---|---|
| сервер | `b.server.history(chat).answer(rows)`, `.fail()`, `.status(401)`, `.always(rows)`; `b.server.chats(rows)`; `b.server.reply(method, path, answer)`; `b.server.expireSession()` |
| сокет | `b.socket.connect()`, `.frame(кадр)`, `.drop()`, `.sent("CHAT_ACK")` |
| приложение Android | `bench({app: true})`; `b.app.lock()`, `.unlock()`, `.notify("silent")`, `.notified()`, `.emit("appBackground")` |
| страница | `b.page.hide()`, `b.page.show()` |
| проверка сессии | `b.signIn(id)` — те же шаги, что в `RequireAuth` |

Запрос истории ждёт, пока тест не ответит: так тест сам решает, что придёт раньше — кадр сокета или ответ сервера.

### Как написать тест

```ts
import {describe, it, expect, afterEach} from "vitest";
import {bench, stop, row} from "./bench";

describe("история 2", () => {
    afterEach(stop);

    it("2.1: сообщение из сокета остаётся после ответа перечитывания", async () => {
        const b = await bench();
        await b.signIn("me");
        b.socket.connect();
        const chat = b.open("c1");
        await b.server.history("c1").answer([]);
        await chat.read;

        const reread = chat.reread();
        b.socket.frame(row({id: "01ARZ3NDEKTSV4RRFFQ69G5FA1", chat: "c1", from: "peer", to: "me", body: "привет"}));
        await b.server.history("c1").answer([]);
        await reread;

        expect(b.screen("c1")?.map((m) => m.text)).toEqual(["привет"]);
    });
});
```

Правила:

- **Имя теста начинается с номера сценария** из `specs/003-message-path/spec.md` (`"2.1: …"`). Строка сценария в `specs/003-message-path/test-matrix.md` заполняется тем же PR. Тест `matrix.test.ts` падает, если у сценария слитой истории нет теста или у теста нет строки.
- **Модули приложения берутся из стенда** — `b.m.outbox`, `b.m.db`, `b.m.api` — а не импортом в начале файла. Стенд на каждый запуск и на `b.restart()` загружает их заново: то, что код держит в переменных модулей, начинается пустым, как после настоящего запуска.
- **Смотреть на экран через стенд**: `b.screen(chat)`, `b.stale(chat)`, `b.queue()`, `b.errors()`. Тогда тест не зависит от того, где сообщения лежат внутри хранилища.
- `b.restart()` убивает приложение (таймеры не срабатывают, запросы остаются без ответа) и запускает его на том же диске. Пользователь после перезапуска не вошёл — нужен `signIn`.
- Хуки проверяются через `renderHook(..., {wrapper: b.wrapper})`.
- `afterEach(stop)` обязателен.

### Чего нельзя подделывать

В тестах пути сообщения нельзя `vi.mock` для `chatApi`, `chatMessages.service`, `sendOutboxThunk`, хранилища истории и остальных файлов из списка `MESSAGE_PATH` (`vitest.config.ts`). Если тесту мешает настоящая часть — не хватает ручки у стенда; её добавляют в `bench.ts`.

Тест, показывающий дефект (A1–A7 в `audit.test.ts` и новые), утверждает поведение как есть и переворачивается тем PR, который дефект чинит.

Исходники как текст тесты читают из `virtual:repo-text`, а не через `?raw`: с `?raw` покрытие считает непокрытый файл покрытым.

### Покрытие

```sh
npm run test:cov
```

Печатает таблицу по файлам пути сообщения (список один — `MESSAGE_PATH` в `vitest.config.ts`) и пишет `coverage/coverage-summary.json`. Столбцы: доля выполненных операторов, ветвей, функций и строк; последний столбец — номера невыполненных строк.

Прогон падает, если строки или ветви по всему списку ниже порога (`thresholds` там же). `npm run ci` и проверка `front` на GitHub зовут тот же прогон. Порог только растёт: PR, поднявший покрытие, поднимает и число; снижать его или убирать файл из списка ради зелёной проверки нельзя — только с причиной в PR. Целевой порог — строки 90 %, ветви 80 %.
